<DocLead>

Every other page on this site describes a specific service. **This one details the underlying operating system that powers them all.**

Proxmox is what turns one small desktop PC into several machines. Instead of installing every service onto a single operating system and hoping they get along, each one gets its own box, its own reset button, and its own way of falling over without taking the others with it.

</DocLead>

<DocSection index="01" title="Why Proxmox?">

The honest version of this starts with something that irritated me enough to change how the lab was built. I would rather leave that gap open than fill it with a tidy invention, so here is the gap.

Before Proxmox, the homelab was running directly on Ubuntu Server. There was nothing particularly wrong with that setup; it worked. The difference was what happened when I broke something. Because the services were running on the bare system, a serious mistake could mean reinstalling the entire operating system just to get back to a clean state.

Nothing was really frustrating me. The problem was simply that everything lived directly on the bare system. If I broke the operating system while experimenting, the recovery path was to reinstall the whole thing. As the homelab became more experimental, I wanted a layer that could isolate the things I was running and make mistakes easier to recover from.

I moved to Proxmox because it solved that problem without requiring a separate physical machine for every service. Instead of treating the entire server as one installation, I could divide it into VMs and containers and manage them independently.

What I can describe is the shape of the problem, because most single-server labs walk into the same one.

Put every service on one operating system and it works fine, right up until it doesn't. Then you notice:

- **Nothing is isolated.** One service wants an older library, another wants a newer one, and the package manager makes you pick a winner.
- **There is no clean rollback.** You edited four config files at 1am. Which change was the fix and which is the new bug?
- **Experiments sit next to things you depend on.** Anything unfamiliar gets tested on the machine that serves your media.
- **Everything shares one uptime.** A reboot for one service is a reboot for all of them.

<Callout kind="why" title="The actual pitch">

Virtualization does not stop you breaking things. It makes breaking things cheap to undo. That is the entire reason this layer exists.

</Callout>

</DocSection>

<DocSection index="02" title="So, what is Proxmox?">

If you have only ever installed one operating system per computer, the idea worth sitting with is this: hardware and operating system are not the same decision. One machine can host many, and something has to sit in between handing out the pieces. That something is a hypervisor. Proxmox VE is one.

Four words get used loosely in this space, so here they are pinned down.

<CardGrid columns={2}>
  <Card kicker="One machine, one OS" title="Physical machine" mark="▣">

  A computer as most people meet it. One set of hardware, one operating system installed straight onto it.

  Simple and fast, but all-or-nothing: every service on it shares one fate.

  </Card>

  <Card kicker="The layer in between" title="Hypervisor" mark="◧">

  A thin operating system whose only job is dividing hardware and pretending, convincingly, to be many computers.

  Proxmox VE is a Debian-based hypervisor with a web console. It does not run your services. It runs the things that run your services.

  </Card>

  <Card kicker="Guest, heavier" title="Virtual machine" mark="◩">

  A VM gets virtual hardware: virtual disk, virtual network card, virtual firmware. It boots its own kernel, because as far as it knows it is a real computer.

  That buys strong isolation and the freedom to run an OS unlike the host. The cost is overhead: its own kernel, its own RAM, its own boot.

  </Card>

  <Card kicker="Guest, lighter" title="LXC container" mark="◪">

  An LXC container shares the host kernel and gets an isolated slice of userspace: own filesystem, own processes, own network config.

  It starts in about a second and costs far less RAM. In exchange it must be Linux, and a shared kernel is still a shared kernel.

  </Card>
</CardGrid>

Proxmox VE runs both kinds side by side, so you never have to pick a camp before you know how heavy a new service is.

<Callout kind="gotcha" title="Two things called containers">

LXC containers and Docker containers are not the same thing. LXC holds a whole Linux userspace and behaves like a small machine you log into. Docker packages one application and its dependencies. They stack happily, and often do.

</Callout>

</DocSection>

<DocSection index="05" title="Why this architecture works for me">

All of these are bullet points on the Proxmox website. Here is what they mean in a lab this size.

#### Isolation

A service that breaks breaks alone. A bad upgrade in one guest is invisible to the media server in the next one. The blast radius of a mistake is a single disposable machine.

#### Experimentation

Trying something new stops being a commitment. A guest costs a few minutes and some RAM, and if the idea turns out dull it goes away leaving nothing behind — no stray packages, no orphaned config in `/etc`.

#### Easier recovery

On a single-OS box, recovery means reinstalling and trying to remember what you did. Here it means restoring one guest while the host and everything else stays up.

#### Resource allocation

Cores, RAM and disk are assigned per guest rather than fought over. A background job cannot quietly eat all 24 GB, because it was never given the chance.

#### Snapshots

A snapshot is a point-in-time copy of a whole guest: its disk, and optionally its running memory. Roll back and the guest returns to exactly how it was, mid-uptime.

#### Multiple environments

Two guests can run different versions of the same thing without arguing. Test one, keep serving from the other, swap when you trust it.

<DocSection index="06" title="What I've learned">

After moving to Proxmox, I realised that the virtualization itself was only part of what made it useful. Managing VMs and LXC containers from one place was straightforward, while snapshots and backups made experimenting much less intimidating. Instead of a mistake potentially meaning a full reinstall, I had much more practical ways to recover and continue.

I have already answered this one in practice. When I updated the node, I rebuilt the Proxmox setup from scratch and used that opportunity to change the way I organised the services.

Earlier, I created a separate LXC container for each service, which also meant different IP addresses for each one. In the rebuilt setup, I moved to a simpler model: one Ubuntu VM with Docker installed, with each service running as its own Docker container.

For now, I am happy with that architecture and do not have anything I want to change.

One thing holds generally, and it is why this layer earns its keep: breaking things is far less frightening when a broken experiment cannot take the rest of the lab with it. Curiosity gets expensive when every mistake costs an evening of repair. Make the mistakes cheap and you try more things.

The nicest thing you can say about a working hypervisor is that it gets boring. It sits under everything, stops asking for attention, and pushes the interesting problems up a layer to the services themselves.

</DocSection>
